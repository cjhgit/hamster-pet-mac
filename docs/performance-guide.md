# 性能优化与回归指南

这份文档供后续增加功能、修改仓鼠造型或替换渲染实现时使用。目标是降低长期资源占用，同时保留真实 3D、自由视角、身体形变、原版动作规律和视觉细节。

具体机器上的历史数据见 [2026-10-18 实测记录](3d-performance-20261018.md)。该记录用于理解测试条件和量级，不是所有电脑都必须达到的固定 CPU 数字。

## 先从这里开始

1. 用 `./run.sh` 构建并运行 Release，确认测到的是新进程，而不是安装目录里的旧版本或 Xcode Debug 版本。
2. 先采样真实应用，再用受控场景复现。记录动作、窗口尺寸、Retina 比例、视角、主题、机器、系统版本和代码版本。
3. 保存修改前的结果；每次只切换一个优化因素，保持相同场景顺序、预热和采样时间。
4. 根据调用栈选择修改点，同时观察 CPU、实际提交帧率、GPU 耗时和内存。改完用相同条件重测。
5. 检查画面、步态、暂停与恢复、兼容回退，最后回到真实应用做持续采样。

命令从仓库根目录执行；保持电脑解锁、测试窗口可见。性能采样期间不要同时编译、跑截图测试或另一个性能测试。

```bash
# 构建并启动真实应用；构建成功后才会替换旧进程
./run.sh

# 直接采样当前应用一分钟，随后保存五秒调用栈
python3 scripts/profile-running-app.py --interval 5 --count 12 --sample \
  --output /private/tmp/hamster-profile-before

# 独立测试窗口，覆盖活动、昼夜、睡眠、暂停和隐藏等状态
bash scripts/verify-3d-performance.sh before 20

# 修改后按相同条件执行，使用不同名字保存结果
./run.sh
python3 scripts/profile-running-app.py --interval 5 --count 12 --sample \
  --output /private/tmp/hamster-profile-after
bash scripts/verify-3d-performance.sh after 20
```

真实应用采样输出 `cpu.json` 和 `stacks.txt`。受控结果保存为 `/private/tmp/hamster-3d-performance/before.json`、`after.json`；测试每项活动预热 3 秒，上述命令每项采样 20 秒，完整执行需要数分钟。多个同名应用同时运行时，真实应用采样需用 `--pid` 指定进程。

`/private/tmp` 是临时目录。需要长期保留的结论应另写入 `docs/`，记录测试条件、代码版本和结果；不要只在聊天中留下数字。

## 正确理解测量结果

| 指标 | 含义与限制 |
| --- | --- |
| `cpuPercent` | 进程全部线程的用户态加内核态 CPU 时间除以实际经过时间；100% 表示占满一个核心，不是整机算力的 100%。不含 WindowServer，也不代表 GPU 耗电。 |
| `fps` | 仿真帧数变化，即 `HamsterView.simulationFrames`。不能单独证明画面正在更新。 |
| `renderFPS` | `Hamster3DRenderView.submittedFrames` 的变化，计入已编码并提交呈现的 Metal 帧。不是显示器最终呈现时刻或完整帧间隔分布。 |
| `bodyBackend` | 期望为 `Metal compute`；强制 CPU 曲面时应为 `CPU`。默认性能测试会拒绝静默回退。 |
| `visibleGeometryElements` | 可见场景中非空几何元素的数量，用于观察提交结构变化，不等于 GPU 实际 draw call 数。 |
| `STAGES` | 额外循环中的仿真、场景更新 CPU / 墙钟耗时，以及最近一次 GPU 曲面耗时；不是完整窗口的每帧总耗时。 |
| RSS / physical footprint | 两种不同内存口径。RSS 不能覆盖所有图形资源；也要观察 sample 的 footprint、峰值和长期变化。 |

持续行走和全速跑轮应同时保持约 30 FPS 仿真与提交。静止或睡眠时，仿真继续运行，姿态未变可跳过呈现；暂停、隐藏和休眠后的稳定阶段应停止周期性提交。恢复、调整视角或改变主题时，必要的单次重绘是正常行为。

CPU 平均每帧省 1 ms，在 30 FPS 下约相当于省 3 个 CPU 百分点。因此小分配、重复上传和多余提交也值得检查；不要仅凭单个函数“只有零点几毫秒”就忽略它。

比较时特别注意：

- 自由活动会随机变换行为，两次真实应用的一分钟平均值不是严格配对负载。
- 单独睡眠与跑轮后转入睡眠包含不同过渡；单场景测试也不能直接与完整流程的同名场景作优化比例。
- 行走到目的地后停住会让测试显得更快。现有受控脚本会持续改换目标，并检查实际位移或转身比例。
- 首次着色器编译、资源初始化和热身要与稳定阶段分开观察。小收益需延长采样，必要时交替重复前后版本，避免把噪声写成结论。
- 小窗口、锁屏、窗口被遮挡或掉帧都可能降低负载；这些条件变化不能充当活动场景的优化收益。

### 渲染调度

当前只有仿真时钟推进动作，`SCNRenderer` 向按需绘制的 `MTKView` 编码。`isPaused = true` 关闭 MetalKit 自动刷新；`needsRendering` 去重，场景变化后显式呈现，相机和尺寸改变时标记重绘。

本机曾出现 `SCNView` 指定 30 FPS、仿真实际 30 FPS，但绘制只有约 24 FPS；把首选帧率改高后，又出现按 120 Hz 重复绘制相同姿态。这个现象有设备与系统条件，不能当成所有 SceneKit 环境的定律，但说明首选帧率设置不能替代测量。

新增动画或效果优先接入现有更新和变化检测。新增文字、纹理、光照等状态时，需要使对应的缓存失效并触发一次重绘；不能仅修改数据却沿用旧脏标记。不要为每个功能另外开一套常驻刷新循环。

### GPU 计算与数据传输

身体的场采样、共享边求交、三角化、平滑、法线与毛色坐标都在 Metal compute 中完成。CPU 提供小规模参数，SceneKit 直接使用生成的 Metal 顶点和索引缓冲。

手脚、尾巴和嘴部仍在 CPU 侧生成形变，但按材质合批，直接写入共享 Metal 顶点缓冲。顶点、法线、纹理坐标和描边共享输出，避免经 `Data` 交给 SceneKit 后逐属性分配与上传。本次单因素配对测量因此省了约 1.27 个 CPU 百分点，见历史实测记录。

新增部件先检查能否复用现有材质和批次，不要只因顶点少就忽略对象分配、上传与提交成本。常规播放不能为了计算包围盒、调试显示或统计而每帧读回完整 GPU 网格或画面；`positionsForInspection()`、离屏截图和 CPU 参考曲面用于显式检查。

### 缓冲生命周期与同步

交给 SceneKit 的输出在该帧之后保持不可变。旧资源可能仍被 SceneKit 或在途 GPU 命令持有，不能只看 CPU 已切换到下一帧就覆盖缓冲。

当前身体输出优先使用 16 MiB Metal 堆，合批四肢使用 1 MiB 堆；自动分配只在旧资源释放后回收空间，容量不足回退到独立缓冲。堆是减少分配开销，不是允许复写旧帧的循环数组。工作区和参数缓冲可以复用，是因为前一次计算已经完成。

身体计算目前在提交给 SceneKit 前等待完成，并读取少量计数。调用栈中的 `waitUntilCompleted` 可能是线程休眠，墙钟等待不能直接算为 CPU 忙计算。若要改成异步，必须同时设计计数可用时机、跨队列依赖、输出生命周期、背压和失败回退，不能只删掉等待。

身体输出堆使用未追踪 hazard 的资源；现有计算阶段间有显式缓冲屏障，SceneKit 使用前已有完成同步。更改队列、编码器、存储模式或同步策略时，这些依赖必须重新核对。当前呈现最多允许三个在途帧，不通过忙等等待名额。

### 缓存、合批与局部坐标

复用固定三角形索引、圆周采样、腿部角度权重、头部截面和材质。先比较输入或 generation，真正变化时才更新。眼睛与耳缘读取头部局部控制点，整体运动使用节点变换，仍保留眨眼等形变。

比较应相对于最后一次上传的状态，避免连续小位移被逐次忽略、最后积累成明显误差。当前曲面点阈值为 0.0005；身体场签名的位置与方向等参数使用不同阈值。这些是结合现有模型验证过的值，不是可以任意放大的“性能旋钮”。新增参数要补全签名；改变精度需重新验证最大缩放下的轮廓、接触点和动作连续性。

共享材质需要包含所有影响渲染的状态。要给某个节点单独设置双面、发光或其他属性时，复制后再改，避免影响使用同一材质的其他节点。

### 静态网格与描边

普通静态几何可以合并，动态跑轮、灯光和需要独立控制的节点保留语义边界。曾尝试把带反面扩张描边的子树直接 `flattenedClone()`，导致轮心描边及遮挡异常；当前检测到反面描边的对象会保留原层级。

合并后不能只检查“网格数量下降”。应检查正面、背面、侧面、俯视、特写、夜间与透明物体遮挡。几何元素数量只是线索，不是正确性或实际 draw call 的证明。

### 暂停、隐藏与恢复

可见性统一由 `HamsterView` 管理。应用隐藏、最小化、屏幕休眠、会话不活跃或手动暂停时停止仿真；普通隐藏窗口的兜底检查每秒两次，明确暂停或休眠状态不继续轮询。隐藏或挂起时释放绘制表面。

屏幕休眠与会话不活跃是独立状态：屏幕唤醒不能顺便恢复仍未激活的会话。恢复时重置时钟，不补跑隐藏期间的帧。新增定时器、观察者或后台任务也要覆盖停止、恢复和销毁；不要让主仿真停了，新功能还在持续工作。

叠加层目前只在尺寸、显示比例、主题、暂停或水印状态变化时重新布局。新增控件和状态文字同样按输入变化更新。

## 根据症状定位

| 症状 | 先查什么 |
| --- | --- |
| 普通活动 CPU 升高 | 真实进程调用栈、曲面后端、generation / revision 是否每帧无意义变化、新增分配与顶点上传 |
| 仿真 30 FPS，画面却卡 | `submittedFrames`、GPU 错误、在途限制、脏标记与恢复后的 drawable；检查帧间隔，必要时用 Instruments 做帧分析 |
| 静止、暂停仍持续耗 CPU | 自动显示循环、无条件 `needsDisplay`、重复布局、独立 Timer / 轮询、状态浮点抖动 |
| 只在某种主题或视角升高 | 灯光、材质、透明与描边额外通道、分辨率、遮挡；固定同姿态比较 |
| CPU 下降但 GPU / footprint 上升 | 是否只是把计算搬走；检查 GPU 耗时、缓存上限、在途资源与长期稳定性 |
| 内存持续增长 | 资源是否被命令、节点、闭包或缓存长期持有；堆不足后的独立分配是否不断积累 |
| 花屏、锯齿状突刺、偶发形变 | 是否覆盖仍在使用的顶点 / 索引缓冲，屏障或同步是否缺失，容量与布局是否不匹配 |
| 描边缺失或遮挡错误 | 合批材质槽、剔除方向、渲染顺序、深度写入、静态 flatten 的边界 |
| 性能测试全是零帧 | 电脑是否锁屏、窗口是否可见、应用是否隐藏或暂停；先排除按设计挂起 |

可用 `sample` 初步定位，再按问题使用 Instruments 的时间分析、分配或 GPU 工具。采样栈包含等待线程，不要把等待样本数量直接当作 CPU 占比。

## 诊断开关与单因素对照

这些开关都可传给 `./run.sh`；以下 3D 开关也可传给 3D 验证脚本。它们用于归因，不是日常建议配置。

| 开关 | 用途 |
| --- | --- |
| `--hamster-cpu-body` | 强制 CPU 参考曲面，检查 GPU 计算与回退；仍是真实 3D。 |
| `--hamster-unbatched` | 保留各个形变部件独立提交，判断合批收益。 |
| `--hamster-unflattened` | 禁用静态几何合并，检查提交与描边问题。 |
| `--hamster-no-heap` | 禁用输出堆，比较独立缓冲分配及兼容性。 |
| `--hamster-batch-data` | 合批顶点改走 `Data` 上传，比较直接 Metal 缓冲收益。 |

`--hamster-cpu-renderer` 会切回原有二维 Core Graphics 渲染器，是另一条诊断路径；不要拿它运行依赖 `scene3D` 的 3D 性能脚本。

```bash
# 指定场景，仅切换四肢上传方式；其他条件保持一致
bash scripts/verify-3d-performance.sh limb-metal 20 --scenario wheel-day
bash scripts/verify-3d-performance.sh limb-data 20 --scenario wheel-day --hamster-batch-data

# 支持的单场景名：idle、walk-turn、wheel-day、wheel-night、sleep
bash scripts/verify-3d-performance.sh sleep-long 60 --scenario sleep
```

单场景仍包含末尾暂停、隐藏测试与额外阶段计时；它不包含完整流程开头的休眠、会话测试。`--legacy-baseline` 是历史对照辅助标记，不会把当前程序还原为旧实现，也不能充当通用优化前版本。

## 加功能后的回归范围

根据改动选择相关检查。纯文档改动只需校对链接与命令，无需重新执行全套图形和性能测试。

| 改动 | 至少覆盖 |
| --- | --- |
| 新部件、身体轮廓、皮肤或步态 | 动作与多视角验证、持续行走、双向跑轮、实际应用采样 |
| 材质、描边、灯光、纹理或合批 | 场景昼夜 / 多视角验证、相关活动性能、前后截图 |
| 时钟、脏标记、视图或生命周期 | 播放 / 逐帧 / 隐藏 / 休眠恢复验证、完整 3D 性能测试 |
| GPU 内存、曲面参数或同步 | 动作与场景验证、CPU 参考 / 无堆路径、持续运行的内存和 GPU 观察 |
| 共用引擎或二维兼容代码 | 对应原生引擎或二维 Metal 检查，再测实际应用 |

```bash
# 13 种动作、1,560 帧、原版对照与 52 个环绕视角
bash scripts/verify-hamster-motion.sh

# 实体网格、昼夜、多视角、投影、缩放与鼠标输入
bash scripts/verify-3d.sh

# 实际窗口的暂停、逐帧、旋转、隐藏、休眠及恢复呈现
bash scripts/verify-playback.sh

# CPU 参考曲面与禁用堆时的场景兼容
bash scripts/verify-3d.sh --hamster-cpu-body --hamster-no-heap

# 涉及二维路径时再运行
bash scripts/verify-metal.sh
```

动作图像输出到 `/private/tmp/hamster-motion/`，场景截图到 `/private/tmp/hamster-3d/`。后续运行会覆盖同名产物，优化前先复制到另一个目录。现有动作脚本对照的是原版与 3D，不会自动执行历史实测中的 249 张优化前后逐像素比较；需要保存前后图像并单独比较。

视觉核查重点：黑色耳缘、眼睛与嘴、腰臀曲线、四肢连接、脚掌触轮、透明水瓶、轮心描边，以及背面和俯视是否出现穿透或突刺。截图比较要保持同一姿态、相机、尺寸、颜色空间、深度格式和抗锯齿设置；当前 3D 使用 sRGB 颜色目标、32 位深度和设备支持时的 4× MSAA，清屏颜色按线性值处理。

## 给下一次优化留下记录

每次有效优化至少记录：问题动作与复现方式、原调用栈热点、修改的单一因素、机器 / 构建 / 窗口条件、前后 CPU 与仿真 / 提交帧率、GPU 和内存观察、视觉与生命周期验证、仍未验证的范围。

CPU 降低要和实际帧率、画面质量、内存及 GPU 负载一起判断。不要用降帧、缩小窗口、隐藏应用、静默回退或简化仓鼠轮廓替代优化；如果产品明确需要新增质量档位，应单独说明其效果与代价。
